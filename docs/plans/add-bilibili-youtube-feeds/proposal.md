# B站与 YouTube 内容源提案

## 状态

- 方案名称：`add-bilibili-youtube-feeds`
- 当前阶段：需求与技术方案评审
- 本轮范围：B站每周必看、B站指定 UP 主投稿、YouTube 指定频道 Feed

## 为什么要做

学习中心已经具备 RSS 时间线、服务端定时刷新、历史内容合并、日报、收藏、标注和 AI 阅读能力，也具备独立的 YouTube 视频学习工作区。当前缺口不是再建立一套内容阅读系统，而是让没有方便 RSS 地址的视频平台也能进入现有信息流。

对个人用户而言，理想体验是在学习中心里完成“发现更新—筛选内容—阅读或观看—记录与追问”，而不需要先理解 RSSHub 路由、单独维护多个订阅地址或在多个应用之间切换。

## 提议的变化

1. 在现有 RSS 模块中引入可扩展的“内容源”模型，同时继续兼容普通 RSS、Atom 和 RDF 地址。
2. 第一批内置三个轻量来源适配器：
   - B站每周必看；
   - B站指定 UP 主投稿；
   - YouTube 指定频道 Feed。
3. 三类适配器都输出当前 `FetchedRssFeed` 结构，复用现有时间线、日报、收藏、标注、AI 和定时刷新链路。
4. 在设置页增加“内容源”配置，用于保存和验证一个 B站 Cookie。Cookie 仅保存在服务端独立凭证文件中，不通过 `/api/state` 返回浏览器。
5. YouTube Feed 中的视频可以按需加入现有视频学习模块；获取字幕和视频详情只在用户主动进入学习时发生。
6. 不引入完整 RSSHub、Redis、Chromium 或 Playwright；第一版遇到 B站风控时明确提示更新 Cookie，不以浏览器自动化兜底。

## 明确不做

- 不支持小红书、微博、微信公众号等其他平台。
- 不抓取、下载或转存 B站和 YouTube 视频文件。
- 不在第一版实现 B站字幕、弹幕或站内播放。
- 不读取本机浏览器 Cookie 数据库，也不安装浏览器扩展。
- 不支持多个 B站账号或按订阅源绑定不同 Cookie。
- 不部署或托管 RSSHub，不放开普通 RSS 对本机和私网地址的访问限制。

## 关键决策

- “一体化”指统一入口、数据和学习流程，不要求所有采集能力运行在同一个大型依赖栈中。
- B站与 YouTube 仍是 RSS 页面中的视频类订阅源，不新增一级导航。
- B站 Cookie 是可选增强：每周必看不依赖 Cookie；UP 主投稿优先匿名请求，在风控或登录校验失败时使用已配置 Cookie 重试。
- YouTube 频道更新优先消费官方 Atom Feed；现有 `youtubei.js` 只负责解析频道地址以及用户主动进入视频学习后的详情与字幕。
- 适配器独立实现，只参考 RSSHub 的接口选择、错误场景与测试思路，不复制或内嵌其 AGPL-3.0 源码。

## 预期影响

- 前端：扩展添加订阅源弹窗、订阅源管理、设置页和 YouTube Feed 条目操作。
- 服务端：增加来源分发器、两个平台适配器、B站凭证存储和对应 API。
- 数据：提升 Zustand 持久化版本，为旧订阅源补充标准 RSS 来源描述；Cookie 使用独立文件，不进入 Zustand 状态。
- 调度：继续错峰串行刷新，但按来源设置最小刷新间隔，减少 B站风控和无意义请求。
- 文档：更新 README 中“RSSHub 外置”的绝对表述，改为“少量内置来源 + 可选外部适配层”。

## 主要风险

- B站 WBI 参数和风控策略可能变化，即使配置 Cookie 也不能保证永久稳定。
- YouTube 频道地址解析依赖 `youtubei.js`，需要随依赖升级回归验证。
- 新来源描述必须兼容旧浏览器写回服务端状态的并发保护，否则可能被旧快照覆盖。
- OPML 无法让其他阅读器原生理解 B站内置来源，需要定义无损回导学习中心的扩展字段。
